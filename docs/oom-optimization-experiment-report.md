# ReacNetGenerator Step 3 OOM 分析与内存优化实验报告

- 报告日期：2026-08-02
- 测试分支：`perf/optimize-timed-molecule-output`
- 对应提交：`b332ce99`（`perf: bound Step 3 memory and write timed output to HDF5`）
- 实验范围：同时启用 `--show-molecule-time` 与 `--reaction-event`，并使用 `--nohmm`

## 1. 摘要

本轮工作针对 ReacNetGenerator 在 PATH（Step 3）阶段处理大轨迹时出现的 OOM 问题，重新设计了原子—帧矩阵、multiprocessing 任务传输和时序结果写出流程。

历史作业 `1064886.0` 在 Step 1 和 Step 2 已完成后，于 Step 3 发生 OOM。Slurm 记录为 `OUT_OF_MEMORY`，`MaxRSS=3000.29 G`，`MaxVMSize=3008.41 G`。现有证据能够将故障范围定位到 Step 3，但不足以把根因唯一归到某一行代码。结合旧实现的数据流，主要风险来自完整 `atomeach/conflict` 矩阵的常驻内存、数组随 multiprocessing 任务序列化和预取造成的复制，以及逐帧、逐事件 Python 对象带来的额外峰值。

优化后的实现将完整逻辑矩阵改为临时 `memmap`，按实际分子数量选择紧凑的无符号整数类型，并将 `conflict` 改为布尔类型。route worker 只接收 atom index，reaction worker 只接收 transition index；两类任务均使用 `chunksize=1`，在途任务数限制为约 `2 × nproc`。分子存在时间压缩为连续区间，反应事件在 worker 内聚合为 `Counter`，由主进程增量写入 HDF5。

在 1%、2% 和 5% 三种轨迹规模下，三组作业均正常结束，退出码为 0，HDF5 状态为 `complete`。轨迹帧数从 2,501 增至 12,501，约为原来的 5.00 倍；运行时间从 46 分 12 秒增至 3 小时 38 分 55 秒，为 4.74 倍；HDF5 文件从 12 MB 增至 60 MB，为 5.00 倍；Slurm 记录的峰值内存仅从 11.96 G 增至 16.88 G，为 1.41 倍。结果表明，在当前 5 倍规模、32 CPU、`--nohmm` 的实验范围内，运行时间和输出大小接近随轨迹规模线性增长，而峰值内存没有同步增长，符合本轮优化目标。

这一结果证明当前实现能够完成本轮压力测试，但尚不能证明所有规模下的内存均为常数，也不能直接与历史 3 TB OOM 作业计算内存降幅：原始 OOM 轨迹已删除，两组实验不是同一输入。完整 HMM 路径、不同进程数、临时磁盘峰值和同输入的新旧实现对照仍需补测。

## 2. 问题背景与故障定位

### 2.1 历史 OOM 记录

表 1. 历史 OOM 作业的阶段状态

| 阶段 | 状态 | 已知耗时或结果 |
| --- | --- | ---: |
| Step 1 | 完成 | 66,532.411 s |
| Step 2（HMM） | 完成 | 375.110 s |
| Step 3（PATH） | OOM，未完成 | `MaxRSS=3000.29 G` |
| 分子时间输出 | 已生成 | `.molecules.csv` 非空 |
| 反应事件输出 | 未完成 | `.reactionevent.csv` 为空 |

该顺序说明 OOM 发生于 Step 3，并且很可能位于分子时间输出完成之后、反应事件输出完成之前。它可以排除“仅仅因为最终文本文件太大”这一单一解释，但仅凭作业日志无法将故障唯一定位到某个函数或某次内存分配。

### 2.2 旧实现中的内存放大路径

Step 3 的基础状态是两个原子—帧矩阵：

$$
\texttt{atomeach}[N,T],\qquad \texttt{conflict}[N,T]
$$

其中，$N$ 为原子数，$T$ 为分析帧数。在典型 64 位环境中，旧实现的两个矩阵均使用平台整数类型，逻辑空间约为：

$$
M_{\text{old matrix}} \approx 16NT\ \text{bytes}
$$

矩阵本身并不是唯一风险。旧 route 任务会把一条原子的完整时间序列交给 worker，旧 reaction 任务会把相邻帧的 `atomeach/conflict` 数组序列化后交给 worker。对于单个任务数组大小为 $S_{\text{item}}$、`chunksize` 为 $C$ 的情况，仅一个任务批次的数据量即可近似写为：

$$
M_{\text{batch}} \approx C \times S_{\text{item}}
$$

早期实验斜率曾估算：旧 route 路径在 `chunksize=100` 时，每个进程的批次数据约为 2.25 GB，即单条序列约为 22.5 MB。该数值是用于解释风险的估算，而不是对历史 OOM 峰值的完整内存分解。实际峰值还可能包含矩阵常驻页、pickle 临时对象、进程池队列、预取结果、排序缓冲、Python 聚合对象以及输出 staging。

### 2.3 为什么没有采用“读取机器剩余内存”自动扩容

初版方案曾考虑按单条数组的实际字节数，将每个批次限制在固定的 32 MiB 预算内：

$$
C_{\text{memory}}=
\max\left(1,\left\lfloor
\frac{32\ \text{MiB}}{S_{\text{item}}}
\right\rfloor\right)
$$

该方案优于按“轨迹是 1% 还是 5%”设置经验参数，也比读取节点当前可用内存更可复现。后者容易受到 Slurm 分配边界、同节点其他作业、page cache、共享页和运行时波动影响。

但是，固定字节预算只能限制批次复制，不能解决以下问题：

1. 单个数组本身超过预算时，`chunksize` 最低只能降到 1；
2. 完整 `atomeach/conflict` 矩阵仍可能常驻于主进程或被 worker 复制；
3. reaction 任务仍需反复序列化相邻帧数组；
4. 逐帧展开结果和主进程聚合对象仍可能形成新的峰值。

因此，最终实现没有使用动态 32 MiB 批次，而是采用更直接的索引任务和磁盘映射共享数据。固定字节预算仍可作为其他数组型 multiprocessing 调用的通用策略，但不是本次已验证实现的一部分。

## 3. 优化设计与实现

### 3.1 磁盘映射的原子—帧矩阵

`atomeach` 和 `conflict` 被写入临时 `memmap`，不再作为普通 NumPy 大数组常驻于每个进程。`atomeach` 根据分子实例数量选择能够容纳其 ID 的最小无符号整数类型，`conflict` 使用 `bool`。当前矩阵的逻辑空间为：

$$
M_{\text{current matrix}} = NT\left(S_{\text{molecule id}}+1\right)
$$

其中 $S_{\text{molecule id}}$ 为 1、2、4 或 8 bytes，因此总逻辑空间约为 $2NT$ 至 $9NT$ bytes。该空间仍随轨迹长度线性增加，但主要消耗临时磁盘；实际 RSS 由访问模式、驻留页、进程开销和写出缓冲共同决定。

相关实现见 [`_AtomFrameStore`](../reacnetgenerator/_path.py)。

### 3.2 索引任务与受限预取

worker 初始化时只读映射共享矩阵及必要的名称、原子类型数据。任务队列不再携带完整行或列：

- route 任务只传 `atom_index`；
- reaction 任务只传 `transition_index`；
- 两类任务均使用 `chunksize=1`；
- `max_inflight=max(2, 2 × nproc)`，即平均每个 worker 最多约两个在途任务。

这项修改同时限制了 pickle 负载、队列预取和待处理结果的数量。`max_inflight` 始终不小于 `chunksize`，避免生产者在凑齐一个批次之前被信号量阻塞。

相关实现见 [`_printatomroute`](../reacnetgenerator/_path.py)、[`ReactionsFinder.findreactions`](../reacnetgenerator/_reaction.py) 和 [`run_mp`](../reacnetgenerator/utils.py)。

### 3.3 紧凑结果与增量写出

分子时间信息不再展开为“每个分子 × 每个存在帧”的行集合，而是将连续存在帧合并为闭区间 `[start_frame, end_frame]`，写入 HDF5 的 `molecule_ranges`。

反应任务在 worker 内对单个 transition 的反应进行 `Counter` 聚合，只返回 `(transition_index, Counter)`。任务允许乱序完成；HDF5 使用 `block_start/block_length` 将紧凑事件块映射回 transition index。主进程收到结果后立即 staging，不保留全量逐事件 Python 对象。

输出文件使用同目录临时文件、文件锁、状态属性和原子发布。只有完成全部写入并标记为 `complete` 后才替换正式文件；失败构建不会覆盖已有完整结果。相关实现见 [`TimedOutputStore`](../reacnetgenerator/_timedoutput.py)。

### 3.4 开发阶段回归验证

优化记录中已有以下自动化验证结果：

- 新增 HDF5/OOM 路径测试：16 passed；
- 其他本地回归测试：32 passed；
- 相关旧接口测试：9 passed；
- 格式、导入排序、编译和 `git diff --check` 均通过。

完整旧测试中的远程下载用例受当时网络沙箱限制，GUI 用例受无显示环境限制。上述结果用于验证实现和兼容性，不替代下面的大轨迹资源实验。

## 4. 实验目的与方法

### 4.1 实验问题

本次实验回答三个问题：

1. 同时启用分子时间和逐时刻反应事件输出时，优化后的流程能否完整结束并生成结构有效的 HDF5；
2. 输入轨迹规模增加时，运行时间和输出文件是否保持可解释的扩展趋势；
3. 峰值内存是否仍与轨迹帧数近似同比增长。

### 4.2 测试配置

表 2. 压力实验配置

| 项目 | 配置 |
| --- | --- |
| 代码 | `perf/optimize-timed-molecule-output` / `b332ce99` |
| 功能 | `--show-molecule-time` 与 `--reaction-event` 同时开启 |
| HMM | 关闭（`--nohmm`） |
| CPU | 32 |
| 输入规模 | 同一实验序列的 `pct_01`、`pct_02`、`pct_05` 子集 |
| 分析参数 | 三组保持不变 |
| 资源记录 | Slurm `sacct` |
| 正确性检查 | 作业状态、退出码、HDF5 `status` 及关键数据集行数 |

现有原始日志明确显示 `pct_02` 请求 256 G 内存、`pct_05` 请求 64 G 内存；`pct_01` 的完整 `sacct` 原始行未保留在本报告材料中。请求内存只决定调度上限，本报告比较的是 `sacct` 记录的实际 `MaxRSS`。

### 4.3 指标定义

- 轨迹规模：HDF5 `frames/timestep` 的帧数；
- 运行时间：Slurm 作业 elapsed time；
- 峰值内存：`sacct --units=G` 输出的 `MaxRSS`；
- 输出大小：最终 `.timeline.h5` 文件大小；
- 结构完整性：作业退出码为 0，且 HDF5 根属性 `status=complete`；
- 内容规模：分子实例数、分子存在区间数、反应类型数和反应事件总数。

## 6. 结果分析

### 6.1 功能与文件完整性

三组作业均以退出码 0 结束，HDF5 状态均为 `complete`。分子实例、分子存在区间、反应类型和反应事件数据均非空，说明两个新增功能在当前测试范围内可以同时完成。`pct_05` 在仅请求 64 G 内存的情况下完成，实际 `MaxRSS` 为 16.88 G，约占请求值的 26.4%。

这证明了文件完成状态和数据结构有效，但不等同于化学结果已经与旧实现逐项一致。最终合入前仍应对 `.moname`、`.route`、`.reactionabcd` 以及时序事件聚合结果进行同输入精确对照。

### 6.2 运行时间接近线性扩展

从 `pct_01` 到 `pct_05`，帧数增加 5.00 倍，运行时间增加 4.74 倍。每 1,000 帧的平均运行时间分别约为 18.47、18.30 和 17.51 分钟。当前数据没有显示明显的超线性时间恶化，也未观察到由全量排序或聚合导致的明显超线性增长。

由于只有三个输入规模，且没有各阶段细分计时，不能据此确定渐近复杂度，也不能区分计算、memmap page fault 和 HDF5 写入各自的耗时贡献。

### 6.3 峰值内存未随帧数同比增长

帧数增加 5.00 倍时，峰值内存从 11.96 G 增至 16.88 G，仅增加 41.1%。相比之下，分子存在区间数增加 5.49 倍，反应事件总数增加 8.85 倍。即使输出内容复杂度增长快于帧数，峰值内存仍保持缓慢增长，说明区间化、局部 `Counter` 聚合和增量写出有效避免了全量 Python 结果在内存中累积。

峰值内存仍有小幅增长是合理的：`memmap` 只改变后备存储和共享方式，不保证所有映射页永不驻留；分子名称、route 结果、HDF5 缓冲、进程运行时和操作系统缓存仍会占用内存。因此，本实验支持“内存放大路径已得到控制”，但不支持“内存与轨迹长度完全无关”的绝对结论。

### 6.4 输出大小与轨迹规模基本一致

轨迹帧数增加 5.00 倍，HDF5 文件由 12 MB 增至 60 MB，也增加 5.00 倍。分子存在区间增加 5.49 倍，而反应事件总数增加 8.85 倍，说明 HDF5 大小不仅由帧数决定，还受区间连续性、物种字典复用和事件聚合效果影响。在本轮数据上，最终文件仍表现为近似线性增长。

### 6.5 与历史 3 TB OOM 的关系

历史作业证明旧流程可以在 Step 3 形成约 3 TB 的内存峰值；本轮实验则证明新流程能在最大 12,501 帧的 `pct_05` 输入上以 16.88 G 完成。由于历史原始轨迹已经删除，二者的原子数、帧数、分子数、事件密度和运行参数无法做同输入对齐，因此不能将 `3000.29 / 16.88` 解释为优化倍数。

本轮实验的有效结论是：在相互可比的 `pct_01`、`pct_02` 和 `pct_05` 新实现测试中，输入帧数增加约 5 倍，峰值内存只增加约 1.41 倍。它验证了扩展趋势，而不是完成了历史作业的严格复现。

## 7. 结论

1. 历史 OOM 可以定位到 Step 3，但现有日志不足以唯一确定单行根因。旧实现中的完整整数矩阵、数组型 multiprocessing 任务、默认大批次、预取和逐事件对象共同构成了可信的内存放大路径。
2. 仅按固定字节预算自动调整 `chunksize` 可以缓解批次复制，但不能消除单项大数组、完整矩阵常驻和逐帧结果累积，因此未作为最终方案。
3. 已实现的 `memmap + 紧凑 dtype + 索引任务 + chunksize=1 + 受限 max_inflight + 紧凑结果 + HDF5 增量写出` 从数据表示、IPC 和结果生命周期三个层面同时限制了峰值内存。
4. 三组 `--nohmm` 双功能实验全部成功。帧数增加 5.00 倍时，运行时间增加 4.74 倍，文件大小增加 5.00 倍，峰值内存仅增加 1.41 倍，符合本轮内存优化和近线性扩展目标。
5. 当前结果应表述为“通过 5% 范围内的阶段性验证”，而不是“彻底消除所有 OOM”。完整 HMM、多进程数、临时磁盘和更大输入仍需继续验证。

## 8. 局限性与后续实验

建议按以下顺序补全证据：

1. 同输入新旧对照：在旧实现仍能完成的 `pct_01` 或更小输入上，保持所有参数一致，对比 wall time、MaxRSS、临时空间和输出语义；这是量化优化收益的必要条件。
2. 结果一致性：精确比较 `.moname`、`.route` 和 `.reactionabcd`，并验证由 HDF5 `reaction_events` 聚合出的总数与 `.reactionabcd` 一致。
3. 启用 HMM：使用与生产作业一致的 HMM 配置重复 1%、2% 和 5% 测试，避免把 `--nohmm` 结果直接外推到完整流程。
4. 并行度矩阵：在 1、8、32 和 96 进程下记录 Step 3 各子阶段耗时与峰值内存，确定吞吐与进程开销的最佳平衡点。
5. 临时存储监测：记录 `atomeach/conflict` memmap 峰值空间、HDF5 临时文件峰值、I/O 吞吐、major page faults 和临时目录所在文件系统，验证 OOM 没有被简单转化为磁盘不足或 I/O 抖动。
6. 逐级放大：在资源监控和失败清理验证完成后，再按 10%、更大比例直至生产规模逐级放大；每一级均保留 `sacct`、HDF5 完整性检查和临时空间记录。
7. 分阶段监控：为 SMILES、矩阵构建、route、reaction 和 HDF5 finalize 分别记录 wall time、RSS 与临时空间，以便确认剩余 11.96–16.88 G 峰值的具体来源。

只有在同输入对照、完整 HMM 和生产规模测试均完成后，才能最终判断历史 OOM 是否已被完全解决，并给出可靠的生产资源建议。
